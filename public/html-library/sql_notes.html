🗂️ SQL Command Categories

★ ImportantDADSMLE

Every SQL statement belongs to one of five families:

CategoryStands forCommandsPurpose
DDLData Definition LanguageCREATE, ALTER, DROP, TRUNCATEDefines/changes the structure of objects (tables, databases)
DMLData Manipulation LanguageINSERT, SELECT, UPDATE, DELETEDirectly manipulates the data itself (CRUD)
TCLTransaction Control LanguageBEGIN, COMMIT, ROLLBACK, SAVEPOINTControls grouping of statements into safe, all-or-nothing transactions
DCLData Control LanguageGRANT, REVOKEControls who can access/modify what
DQLData Query LanguageSELECTRetrieves data (some group SELECT under DML instead — both views are common)
💡 Beginner tip (from the original notes)
Always use COMMIT and ROLLBACK carefully to avoid unintended changes, especially on shared/production databases. Run the equivalent SELECT first to see exactly which rows a DML statement will touch before you run the real UPDATE/DELETE.

SQL vs NoSQL

SQLNoSQL
Data shapeRows & columns, fixed schemaJSON/key-value, documents, or graphs — flexible schema
Best forBanking-style systems needing complex queries & transactionsSocial media, IoT streams, real-time analytics, big data
ExamplesPostgreSQL, MySQL, Oracle SQLMongoDB, Redis, Cassandra, DynamoDB

PgAdmin is the GUI most commonly used to browse and query a PostgreSQL database (used throughout this course).

💼 Manager's Corner

Why we use this

SQL is the lingua franca of structured data — nearly every analytics stack, warehouse, and ML feature pipeline reads from a relational store at some point, even if the app itself runs on NoSQL.

What the manager actually wants

"Can you pull the number I asked for, accurately, without touching anything you shouldn't?" Managers rarely care about DDL vs DML — they care that you know the difference between a read-only SELECT and a statement that changes data, and that you're careful with the latter.

Alternatives

NoSQL (MongoDB, DynamoDB) for unstructured or very high write-throughput apps; pandas/Polars for ad-hoc analysis on local files; Spark SQL / BigQuery / Snowflake SQL when the data is too big for a single Postgres instance. The SQL syntax you learn here transfers almost directly to all of them.

🏗️ Databases & Tables

DADS
-- create / drop a database
CREATE DATABASE company;
DROP DATABASE company;

-- create a table inside it
CREATE TABLE employee(
    emp_id     SERIAL PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    position   VARCHAR(50),
    department VARCHAR(50),
    phone      VARCHAR(15) UNIQUE,   -- see gotcha below
    hire_date  DATE,
    salary     NUMERIC(10,2)         -- 10 total digits, 2 after the decimal
);
⚠️ Gotcha (corrected from original notes)
The original notes had PHONE INT(10). That's invalid PostgreSQL — INT does not take a length modifier (that's a MySQL-ism). Also, phone numbers should almost never be a numeric type: they can have leading zeros, + country codes, or dashes, and you never do arithmetic on them. Use VARCHAR(15) or similar instead.
💼 Manager's Corner

Why we use this

The table schema is the contract every downstream report, dashboard, and model feature relies on. Get it wrong once and every number built on top of it is wrong too.

What the manager actually wants

Assurance that changing a table (adding a column, renaming one) won't silently break an existing dashboard or pipeline that reads from it.

Alternatives

Cloud data warehouses (Snowflake, BigQuery, Redshift) for analytics-scale tables instead of a transactional Postgres database; schema-less document stores when the structure genuinely varies row to row (rare for reporting use cases).

💼 Manager's Corner

Why we use this

Picking the right type is what makes math correct (NUMERIC vs FLOAT avoids penny-rounding bugs in financial reports) and queries fast (proper types are indexable and compact).

What the manager actually wants

Numbers that reconcile exactly with finance/accounting — this is precisely why money columns must be NUMERIC, never FLOAT/REAL, which can introduce tiny rounding errors.

Alternatives

Storing everything as text and casting in the application layer (fragile, avoid); using FLOAT/DOUBLE deliberately for ML feature columns where exact precision doesn't matter and speed/memory does.

🔒 Constraints

★ ImportantDADS

Constraints are rules enforced on table data to guarantee accuracy, consistency, and integrity. They're applied to columns/tables at creation time or added later via ALTER TABLE.

ConstraintMeaning
NOT NULLColumn can never be empty
UNIQUENo two rows may share this value
PRIMARY KEYUnique + not null — identifies each row
FOREIGN KEYValue must exist in another table's referenced column
CHECKCustom boolean condition the value must satisfy
DEFAULTAuto-fills a value when none is given
EXCLUSIONGeneralizes UNIQUE to arbitrary comparison operators (advanced)
CREATE TABLE students1(
    student_id SERIAL PRIMARY KEY,
    name       VARCHAR(50) NOT NULL,
    email      VARCHAR(100) UNIQUE,
    age        INTEGER CHECK (age >= 18),
    reg_date   TIMESTAMP DEFAULT CURRENT_TIMESTAMP   -- auto-filled if omitted
);

INSERT INTO students1 (student_id, name, email, age)   -- reg_date not specified
VALUES (101, 'Nikhil', 'nk813@gmail.com', 21),
       (102, 'Nitin',  'nit333@gmail.com', 19),
       (103, 'Manya',  'man737@gmail.com', 20);
💼 Manager's Corner

Why we use this

Constraints are automated data-quality guardrails — they stop garbage data at the door instead of you discovering "why does this dashboard show a negative age" three weeks later.

What the manager actually wants

Confidence that "the data is clean" without personally auditing every load — constraints are the cheapest way to earn that trust.

Alternatives

Enforce quality downstream instead of at the schema level: dbt tests, Great Expectations, or application-level validation. These are more flexible but reactive — bad data can land before you catch it.

✏️ INSERT / UPDATE / DELETE / TRUNCATE

★ ImportantDADSMLE
-- INSERT (emp_id omitted: SERIAL auto-increments it)
INSERT INTO employee (name, position, department, hire_date, salary)
VALUES ('Nikhil', 'Data Analyst', 'Data Science', '2022-05-15', 65000.00),
       ('Nitin',  'Data Analyst', 'Data Science', '2022-05-20', 60000.00);

-- UPDATE
UPDATE employee2
SET salary = 60000, position = 'Data Finance'
WHERE department LIKE 'Data Science';

-- DELETE a row
DELETE FROM employee WHERE emp_id = 105;

-- TRUNCATE wipes all rows but keeps the table structure
TRUNCATE TABLE employee;
-- identity counter is NOT reset by default; next insert continues where it left off
TRUNCATE TABLE employee RESTART IDENTITY;   -- resets the SERIAL counter too
⚠️ DELETE vs TRUNCATE vs DROP
  • DELETE FROM t WHERE ... — removes matching rows, keeps table, can be rolled back, fires triggers, slower on huge tables.
  • TRUNCATE TABLE t — removes all rows instantly, keeps structure, much faster, minimal logging.
  • DROP TABLE t — removes the table and its structure entirely.
💼 Manager's Corner

Why we use this

This is how you correct data, load new records, or purge stale ones. As a DA you'll patch reference tables; as an MLE you'll write processed features back into a feature table.

What the manager actually wants

"If this update is wrong, can we roll it back?" — this is exactly why transaction discipline (see Transactions) matters more than the UPDATE syntax itself.

Alternatives

Bulk ETL/ELT tools (Airbyte, Fivetran, dbt) instead of manual INSERT/UPDATE for production pipelines; an ORM (SQLAlchemy) for programmatic manipulation from Python.

🛠️ ALTER TABLE

DADS
-- 1. rename a column
ALTER TABLE employee2 RENAME COLUMN name TO emp_name;

-- 2. change a column's datatype (USING is required for non-trivial casts)
ALTER TABLE employees
ALTER COLUMN salary TYPE INTEGER USING salary::INTEGER;

-- 3. add a constraint to an existing column
ALTER TABLE students ALTER COLUMN name SET NOT NULL;

-- 4. drop a constraint
ALTER TABLE students DROP CONSTRAINT age_check;

-- 5. rename the whole table
ALTER TABLE students1 RENAME TO students;

-- 6. add / drop a column
ALTER TABLE employees ADD COLUMN email VARCHAR(100);
ALTER TABLE employee2 DROP COLUMN salary;
💼 Manager's Corner

Why we use this

Schemas evolve as business requirements change — you'll constantly need to add a tracked field without taking the system down.

What the manager actually wants

"Will this lock the table and take down the app while it runs?" On large production tables, some ALTER operations (like changing a column type) can hold a lock for a long time — this is a real concern, not a hypothetical one.

Alternatives

Migration tools (Alembic, Flyway, Liquibase) track ALTER statements in version control and can run them more safely than ad hoc console changes.

📥 Importing CSV Data

★ ImportantDADSMLE

PostgreSQL's COPY command bulk-loads a CSV straight into a table — far faster than row-by-row INSERTs.

CREATE TABLE employee (
    employee_id  INT PRIMARY KEY,
    first_name   VARCHAR(20) NOT NULL,
    last_name    VARCHAR(20) NOT NULL,
    department   VARCHAR(20),
    salary       NUMERIC(10,2),
    joining_date DATE,
    age          INT
);

COPY employee (employee_id, first_name, last_name, department, salary, joining_date, age)
FROM 'E:\study\SQL\12_sql_emp_csv.csv'
DELIMITER ','
CSV HEADER;

Real files are messy. Here the joining_date column was formatted DD-MM-YYYY and Postgres expects YYYY-MM-DD, so it was fixed in pandas before loading:

import pandas as pd

df = pd.read_csv('13_employee_data_with_error.csv')
df['joining_date'] = pd.to_datetime(df['joining_date'], format='%d-%m-%Y').dt.strftime('%Y-%m-%d')
df.to_csv('13_employee_data_with_error.csv', index=False)
💡 Tip
This "fix it in pandas, then COPY it into SQL" pattern is extremely common in real DA/DS work — raw CSV exports almost never arrive in the exact date format or encoding the database expects.
💼 Manager's Corner

Why we use this

Real data almost always arrives as a CSV/Excel/API dump. Getting it into SQL correctly — right types, right date formats, no silent truncation — is a huge share of a data analyst's actual job.

What the manager actually wants

"Is the data actually correct in the table?" Not "did the load finish without error" — a load can succeed and still have silently mis-parsed dates or truncated strings.

Alternatives

pandas df.to_sql() for smaller loads from Python; orchestrated pipelines (Airflow + COPY) for recurring loads; cloud-native bulk loaders (Snowflake COPY INTO, BigQuery load jobs) at warehouse scale.

🔎 Operators — the WHERE clause toolkit

★ ImportantDADSMLE

Arithmetic

-- 10% bonus on salary
SELECT first_name, salary, (salary * 0.1) AS bonus FROM employee3;

-- annual salary + 5% increment, and the resulting new monthly salary
SELECT first_name, salary,
       (salary * 12)   AS annual_salary,
       (salary * 0.05) AS increment_salary,
       (salary * 1.05) AS new_salary
FROM employee3;   -- operators: + - * / %

Comparison

-- =  !=  <>  <=  >=  <  >
SELECT * FROM employee3 WHERE age = 30;
SELECT * FROM employee3 WHERE age != 30;      -- same as <>
SELECT * FROM employee3 WHERE salary > 50000;

Logical

-- AND / OR / NOT
SELECT * FROM employee WHERE age >= 60 AND salary >= 50000;
SELECT * FROM employee WHERE age >= 60 OR  salary >= 50000;
SELECT * FROM employee WHERE NOT (department = 'IT');

BETWEEN, LIKE, IN

-- range check
SELECT * FROM employee4 WHERE salary BETWEEN 40000 AND 60000;

-- pattern match: % = any sequence, _ = single char
SELECT * FROM employee4 WHERE email LIKE '%gmail.com';
SELECT * FROM employee4 WHERE email NOT LIKE '%gmail.com';
SELECT * FROM employee4 WHERE LOWER(email) LIKE '%gmail.com';  -- case-safe match

-- membership check
SELECT * FROM employee4 WHERE department IN ('Finance', 'Marketing');
SELECT * FROM employee4 WHERE department NOT IN ('Finance', 'Marketing');

IS NULL, ORDER BY, LIMIT, DISTINCT

-- find missing values (never use = NULL, it never matches)
SELECT first_name, last_name, email FROM employee4 WHERE email IS NULL;

-- sort  (ASC is the default)
SELECT first_name, last_name, salary FROM employee4 ORDER BY salary DESC;

-- top N rows
SELECT first_name, last_name, salary FROM employee4
ORDER BY salary DESC LIMIT 5;

-- unique values / count of unique values
SELECT DISTINCT department FROM employee4;
SELECT COUNT(DISTINCT department) AS total_dept FROM employee4;
💼 Manager's Corner

Why we use this

This is the bread and butter of every WHERE clause you'll ever write to slice data for a report or feature set.

What the manager actually wants

The filtered number that matches their mental definition of the question — e.g. "active customers" needs a precise, agreed-upon definition before you filter, or your number and theirs won't match.

Alternatives

The same filtering logic expressed in pandas (df[df.col > x]) or a BI tool's filter UI — SQL is usually faster and more reproducible when the data lives at the source.

📊 Aggregate Functions + GROUP BY / HAVING

★ ImportantDADS✚ GROUP BY/HAVING added

Aggregate functions collapse a set of rows into a single value: COUNT(), SUM(), AVG(), MAX(), MIN().

SELECT COUNT(*) AS total_products FROM products;

SELECT COUNT(*) AS total_electronics_over_50k
FROM products
WHERE LOWER(category) = 'electronics' AND price > 50000;

SELECT SUM(quantity) AS total_qty FROM products;
SELECT AVG(price)    AS avg_price  FROM products;
SELECT MAX(price), MIN(price) FROM products;
✚ Added — GROUP BY / HAVING
The original notes used aggregates only over the whole table. In practice you almost always want them per group (per category, per department, per month) — that's GROUP BY. To filter on an aggregated value, you need HAVING, not WHERE (WHERE runs before grouping, HAVING runs after). 
-- revenue per genre (from the bookstore project)
SELECT b.genre, SUM(o.quantity) AS number_of_books_sold
FROM Books b
JOIN Orders o ON b.book_id = o.book_id
GROUP BY b.genre;

-- customers with at least 2 orders  -> filter AFTER aggregation = HAVING
SELECT c.name, COUNT(o.order_id) AS order_count
FROM Orders o
JOIN Customers c ON o.customer_id = c.customer_id
GROUP BY c.name
HAVING COUNT(o.order_id) > 1;
⚠️ WHERE vs HAVING
WHERE filters individual rows before grouping. HAVING filters the grouped results after aggregation. Trying to write WHERE COUNT(*) > 1 is a classic beginner error — it must be HAVING COUNT(*) > 1.
💼 Manager's Corner

Why we use this

This is reporting. COUNT/SUM/AVG grouped by a dimension is what's behind almost every KPI tile on a dashboard.

What the manager actually wants

A single summary number, broken down by team/region/month — and confidence that HAVING is applied correctly so "customers with 2+ orders" doesn't secretly include customers with just 1.

Alternatives

pandas .groupby().agg(), Excel Pivot Tables, or a BI tool's built-in aggregation — SQL aggregation pushes the computation to the database and scales to billions of rows, which pandas/Excel cannot.

🔤 String Functions

DADS
SELECT UPPER(product_name) FROM products;
SELECT LOWER(product_name) FROM products;

-- join two columns together with a separator
SELECT CONCAT(product_name, '_', category) AS combined FROM products;

-- substring(column, start_index, length)
SELECT SUBSTRING(product_name, 1, 5) AS shortname FROM products;

SELECT product_name, LENGTH(product_name) AS name_len FROM products;

SELECT REPLACE(product_name, 'phone', 'device') FROM products;

-- first / last n characters
SELECT LEFT(category, 3)  FROM products;
SELECT RIGHT(category, 3) FROM products;
💼 Manager's Corner

Why we use this

Real-world text is messy — inconsistent casing, stray whitespace, embedded codes. String functions clean it before it reaches a report or a model.

What the manager actually wants

"The names in this report look consistent" — no duplicated rows caused by "Laptop" vs " Laptop " being treated as different values.

Alternatives

Regex-heavy cleaning in Python/pandas for complex cases, or a dedicated data-quality tool — SQL string functions are fine for simple, high-volume cleaning right at the source.

📅 Date & Time Functions

★ ImportantDADSMLE
SELECT NOW()           AS now_datetime;
SELECT CURRENT_DATE    AS today;
SELECT CURRENT_TIME    AS now_time;

-- days between two dates (simple subtraction of DATE types)
SELECT product_name, added_date, CURRENT_DATE, (CURRENT_DATE - added_date) AS days_old
FROM products;

-- EXTRACT() pulls a part out of a date
SELECT product_name,
       EXTRACT(YEAR  FROM added_date) AS added_year,
       EXTRACT(MONTH FROM added_date) AS added_month,
       EXTRACT(DAY   FROM added_date) AS added_day
FROM products;

-- AGE() gives a human-readable interval
SELECT product_name, AGE(CURRENT_DATE, added_date) AS age_of_product FROM products;

-- TO_CHAR() formats a date as a string
SELECT product_name, TO_CHAR(added_date, 'DD-MM-YYYY') AS formatted FROM products;

-- DATE_PART() — numeric part of a date; 'dow' = day of week (0=Sun..6=Sat)
SELECT product_name, DATE_PART('doy', added_date) AS day_of_year FROM products;

-- DATE_TRUNC() rounds a timestamp down to a unit — great for "group by month"
SELECT product_name, DATE_TRUNC('month', added_date) AS month_start FROM products;

-- INTERVAL — add/subtract a duration
SELECT product_name, added_date + INTERVAL '6 months' AS renewal_date FROM products;

-- TO_DATE() parses a string into a DATE
SELECT TO_DATE('28-11-2026', 'DD-MM-YYYY') AS converted_date;
💼 Manager's Corner

Why we use this

Nearly every business question is time-boxed — "this month," "last quarter," "days since signup." DATE_TRUNC/EXTRACT/AGE are essential for cohort analysis and for engineering recency features in ML models.

What the manager actually wants

MTD/QTD/YTD numbers that match the company's actual fiscal calendar, not just calendar months.

Alternatives

pandas' .dt accessor for the same operations after export; a dedicated date-dimension table in a warehouse to correctly handle fiscal-year edge cases (common in finance-heavy orgs).

🔀 Conditional Functions — CASE & COALESCE

★ ImportantDADSMLE

CASE — bucket rows by a condition

SELECT product_name, price,
       CASE
           WHEN price >= 50000 THEN 'EXPENSIVE'
           WHEN price >= 10000 THEN 'MODERATE'
           ELSE 'AFFORDABLE'
       END AS price_category
FROM products;

-- stock status assignment (combining CASE with BETWEEN)
SELECT product_name, quantity,
       CASE
           WHEN quantity >= 10             THEN 'IN STOCK'
           WHEN quantity BETWEEN 5 AND 9   THEN 'LIMITED STOCK'
           ELSE 'OUT OF STOCK SOON'
       END AS stock_status
FROM products;

COALESCE — first non-null value

-- fall back to the regular price when there's no discount_price
SELECT product_name,
       COALESCE(discount_price, price) AS final_price
FROM products;
✚ Added — related functions worth knowing
NULLIF(a, b) returns NULL if a = b (handy to avoid divide-by-zero: x / NULLIF(y, 0)). GREATEST(a, b, ...) / LEAST(a, b, ...) return the largest/smallest of a list of values — useful for capping/flooring a column.
💼 Manager's Corner

Why we use this

CASE is business-rule bucketing directly in SQL (age bands, price tiers) — often exactly the "segmentation" a manager asks for by name. COALESCE handles missing data gracefully, which matters for both reporting and ML feature pipelines.

What the manager actually wants

Segments/buckets that match the business definition exactly, and no blank cells breaking the report.

Alternatives

Bucketing in pandas (pd.cut) or in the BI tool itself — SQL CASE keeps the logic versioned in one place and reused by every query touching the table, instead of redefined in every tool.

🪟 Window Functions

★ ImportantDADSMLE

Window functions perform a calculation across a set of rows related to the current row, without collapsing them into one output row like an aggregate does. Great for ranking, running totals, and period-over-period comparisons.

💡 Aggregate vs Window
An aggregate function collapses many rows into one. A window function keeps every row but adds a computed column based on a "window" of related rows (defined by PARTITION BY / ORDER BY). 
-- number rows within each category
SELECT product_name, category, price,
       ROW_NUMBER() OVER (PARTITION BY category ORDER BY price) AS row_num
FROM products;

-- RANK() leaves gaps after ties; DENSE_RANK() does not
SELECT product_name, category, price,
       RANK()       OVER (PARTITION BY category ORDER BY price) AS rank_with_gaps,
       DENSE_RANK() OVER (PARTITION BY category ORDER BY price) AS rank_no_gaps
FROM products;

-- running total, overall and per category
SELECT product_name, category, price,
       SUM(price) OVER (ORDER BY price DESC) AS running_total_overall,
       SUM(price) OVER (PARTITION BY category ORDER BY price DESC) AS running_total_by_cat
FROM products;
✚ Added — LAG/LEAD & NTILE (very common in real analysis)
-- LAG/LEAD: compare a row to the previous/next row -- classic for month-over-month change
SELECT product_name, added_date, price,
       LAG(price)  OVER (ORDER BY added_date) AS prev_price,
       LEAD(price) OVER (ORDER BY added_date) AS next_price,
       price - LAG(price) OVER (ORDER BY added_date) AS change_from_prev
FROM products;

-- NTILE: split rows into N roughly-equal buckets (e.g. quartiles for a feature)
SELECT product_name, price,
       NTILE(4) OVER (ORDER BY price) AS price_quartile
FROM products;
💼 Manager's Corner

Why we use this

Ranking "top N per group," running totals, and period-over-period comparisons — arguably the single most powerful analytical SQL feature. Also a core ML feature-engineering technique (lag features, rolling aggregates).

What the manager actually wants

"Top 5 products per region" or "month-over-month growth" — phrased casually, but it's a window function underneath.

Alternatives

pandas .rank(), .cumsum(), .shift() after pulling data into memory — fine for smaller datasets, but window functions scale inside the database and avoid moving huge tables into memory first.

➕ Set Operators

DADS
OperatorBehavior
UNIONCombine results from both queries, remove duplicates
UNION ALLCombine results, keep duplicates (faster — no dedup step)
INTERSECTOnly rows present in both result sets
EXCEPTRows in the first query that are not in the second
⚠️ Rule for all set operators
Both queries must return the same number of columns, in a compatible order/type. Column names in the output come from the first query. 
SELECT * FROM students_2023
UNION
SELECT * FROM students_2024
ORDER BY student_id;

SELECT * FROM students_2023
INTERSECT
SELECT * FROM students_2024;              -- students enrolled BOTH years

SELECT * FROM students_2024
EXCEPT
SELECT * FROM students_2023;              -- new students in 2024 who weren't there in 2023

SELECT * FROM students_2023
EXCEPT
SELECT * FROM students_2024;              -- students lost between 2023 and 2024 (a churn query!)
💼 Manager's Corner

Why we use this

Combining or comparing similarly-shaped result sets — e.g. reconciling "who ordered in 2023 vs 2024" for churn/retention analysis.

What the manager actually wants

"Who did we lose, who's new" — that's literally EXCEPT and INTERSECT under the hood, even if they never use those words.

Alternatives

pd.concat or merge(..., indicator=True) in pandas for the same set logic once the data is local in memory.

🔗 Joins

★ ImportantDADSMLE
JoinReturns
INNER JOINOnly rows with a match in both tables
LEFT JOINAll rows from the left table; unmatched right columns are NULL
RIGHT JOINAll rows from the right table; unmatched left columns are NULL
FULL OUTER JOINEverything from both sides; NULLs where there's no match either way
CROSS JOINEvery row of table A paired with every row of table B (n × m rows)
SELF JOINA table joined to itself, to compare rows within the same table
SELECT e.employee_id, e.first_name, d.department_name
FROM employee3 e
INNER JOIN departments d ON e.department_id = d.department_id;

SELECT e.employee_id, e.first_name, d.department_name
FROM employee3 e
LEFT JOIN departments d ON e.department_id = d.department_id;   -- keeps employees with no dept

SELECT e.employee_id, e.first_name, d.department_name
FROM employee3 e
FULL OUTER JOIN departments d ON e.department_id = d.department_id;

-- SELF JOIN: find coworkers in the same department
SELECT e1.first_name AS employee_1, e2.first_name AS employee_2, d.department_name
FROM employee3 e1
JOIN employee3 e2 ON e1.department_id = e2.department_id AND e1.employee_id != e2.employee_id
JOIN departments d ON e1.department_id = d.department_id;
✚ Added — the "anti-join" pattern (extremely common in real analysis)
"Customers who have never ordered anything" or "products that were never sold" — this is a LEFT JOIN followed by filtering for NULL on the right side: 
SELECT c.customer_id, c.name
FROM Customers c
LEFT JOIN Orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;   -- customers with NO matching order = anti-join
⚠️ The silent "fan-out" bug
Joining a one-to-many relationship (e.g. one customer → many orders) and then summing a customer-level column will double-count it once per matching order row. Always be sure which side of the join is "one" and which is "many" before aggregating.
💼 Manager's Corner

Why we use this

The single most-used SQL skill for analysts — almost no useful business question lives in one table; you're constantly joining facts (orders) to dimensions (customers, products).

What the manager actually wants

Numbers that aren't inflated or duplicated by an incorrect join — the fan-out bug above is the classic silent way a "total revenue" number ends up wrong without any error being thrown.

Alternatives

pd.merge in pandas after exporting data, or a semantic layer / BI tool that pre-joins a star schema — but joining at the source in SQL is usually the most efficient and auditable approach.

🧩 Subqueries & CTEs ✚ Added

★ ImportantDADSMLE

Not covered in the original notes, but essential once queries get past 2–3 tables. A subquery is a query nested inside another. A CTE (Common Table Expression, the WITH clause) names a subquery so you can reference it like a temporary table — and reuse it more than once in the same statement.

-- subquery in WHERE: books priced above the overall average
SELECT title, price FROM Books
WHERE price > (SELECT AVG(price) FROM Books);

-- CTE: break a multi-step analysis into readable named steps
WITH genre_sales AS (
    SELECT b.genre, SUM(o.quantity) AS total_sold
    FROM Books b
    JOIN Orders o ON b.book_id = o.book_id
    GROUP BY b.genre
)
SELECT genre, total_sold
FROM genre_sales
WHERE total_sold > 10
ORDER BY total_sold DESC;

-- multiple CTEs chained together
WITH customer_spend AS (
    SELECT customer_id, SUM(total_amount) AS spend
    FROM Orders
    GROUP BY customer_id
),
top_spenders AS (
    SELECT * FROM customer_spend WHERE spend > 100
)
SELECT c.name, t.spend
FROM top_spenders t
JOIN Customers c ON c.customer_id = t.customer_id
ORDER BY t.spend DESC;
💼 Manager's Corner

Why we use this

Break a complex analytical question into named, readable steps instead of one unreadable deeply nested query — essential for anything beyond a simple two-table lookup.

What the manager actually wants

They don't care about CTEs by name, but they do care that you can explain and audit exactly how a complex number was derived when someone asks "where did this figure come from?" — CTEs make that possible by giving each step a name.

Alternatives

Temp tables or views for the same decomposition, or pushing the logic into a Python/dbt transformation layer entirely (common once the logic is reused across many reports).

🪞 Views ✚ Added

DADS

A view is a saved query that behaves like a virtual table. A materialized view is the same idea but physically stores the result and must be refreshed.

CREATE VIEW active_customers AS
SELECT c.customer_id, c.name, COUNT(o.order_id) AS order_count
FROM Customers c
JOIN Orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
HAVING COUNT(o.order_id) > 0;

SELECT * FROM active_customers WHERE order_count > 3;   -- query it like a normal table

-- materialized view: physically stored, faster to query, needs manual refresh
CREATE MATERIALIZED VIEW monthly_revenue AS
SELECT DATE_TRUNC('month', order_date) AS month, SUM(total_amount) AS revenue
FROM Orders
GROUP BY 1;

REFRESH MATERIALIZED VIEW monthly_revenue;
💼 Manager's Corner

Why we use this

Package a frequently-reused query (e.g. "active customers") into one object, so every analyst/report uses the exact same definition.

What the manager actually wants

One source of truth for key metrics — avoids the classic "your revenue number doesn't match mine" argument in a meeting.

Alternatives

dbt models (version-controlled, testable views) or a dedicated metrics/semantic layer tool (Cube, LookML) when the same metric needs to be consistent across many BI tools.

⚡ Indexes & EXPLAIN ANALYZE ✚ Added

★ ImportantDSMLE

An index is a lookup structure (usually a B-tree) built on one or more columns so the database doesn't have to scan every row to find a match.

CREATE INDEX idx_orders_customer_id ON Orders(customer_id);

-- see the actual query plan and timing before/after adding an index
EXPLAIN ANALYZE
SELECT * FROM Orders WHERE customer_id = 42;
⚠️ Indexes aren't free
Every index speeds up reads on that column but slows down every INSERT/UPDATE/DELETE (the index has to be maintained too). Index the columns you filter/join on frequently — not every column.
💼 Manager's Corner

Why we use this

As data grows, an unindexed query that took 200ms can take 2 minutes. Understanding indexes and reading a query plan is what separates "it works on my laptop with 100 rows" from "it works in production with 100 million rows."

What the manager actually wants

Dashboards that load in seconds, not minutes — this is almost always a query-performance problem, not a "buy a bigger server" problem.

Alternatives

Materialized views / pre-aggregated summary tables, or moving heavy analytical queries to a columnar warehouse (BigQuery/Snowflake/Redshift), which uses column storage instead of row-based indexes and is built for exactly this kind of scan-heavy analytical query.

🔁 Transactions in Practice (TCL) ✚ Expanded

★ ImportantDADS

The original notes defined BEGIN/COMMIT/ROLLBACK/SAVEPOINT but didn't show them in action. Here's the practical pattern you'll actually use before running a risky UPDATE/DELETE by hand:

BEGIN;

UPDATE employees SET salary = salary * 1.1 WHERE department = 'IT';

-- check the result BEFORE committing
SELECT employee_id, salary FROM employees WHERE department = 'IT';

-- if it looks right:
COMMIT;
-- if something looks wrong instead:
-- ROLLBACK;

-- SAVEPOINT lets you roll back part of a transaction without losing everything
BEGIN;
UPDATE employees SET salary = salary * 1.1 WHERE department = 'IT';
SAVEPOINT after_it_raise;
UPDATE employees SET salary = salary * 1.1 WHERE department = 'HR';
ROLLBACK TO after_it_raise;   -- undoes only the HR update, keeps the IT update
COMMIT;
💼 Manager's Corner

Why we use this

Guarantees that multi-step changes either fully happen or fully don't — critical whenever you (a DA or DS) are doing a manual data fix directly in a production table.

What the manager actually wants

"If something goes wrong halfway through, can we undo it cleanly?" A transaction is literally the answer to that question.

Alternatives

Idempotent, upsert-based ETL pipelines that make re-running the whole job safe, removing the need for careful manual transaction management in the first place.

🔃 UPSERT (ON CONFLICT) ✚ Added

DSMLE

Incremental data loads need to insert new rows and update changed ones without creating duplicates. In PostgreSQL that's INSERT ... ON CONFLICT.

INSERT INTO products (product_id, product_name, price, quantity)
VALUES (3, 'Headphones', 1400.00, 60)
ON CONFLICT (product_id)
DO UPDATE SET price = EXCLUDED.price, quantity = EXCLUDED.quantity;
💼 Manager's Corner

Why we use this

The standard pattern behind almost every scheduled ETL job — daily refreshes need to add new records and update changed ones, never duplicate.

What the manager actually wants

"The daily numbers refresh correctly without creating duplicate rows" — this is exactly what breaks a dashboard silently if it's done wrong.

Alternatives

Full DELETE + INSERT refresh each run (simpler logic, but slower and heavier on large tables); the MERGE statement (the SQL Server/Oracle/Snowflake equivalent concept).

🐍 SQL + pandas / SQLAlchemy ✚ Added

★ ImportantDSMLE

Your course notes already used pandas once (fixing dates before a CSV import). In real DA/DS/MLE work, SQL and Python are used together constantly: SQL narrows down billions of rows to the ones you need, then Python (pandas/scikit-learn) does modeling, plotting, or further shaping.

import pandas as pd
from sqlalchemy import create_engine

engine = create_engine("postgresql://user:password@localhost:5432/company")

# pull a query straight into a DataFrame
df = pd.read_sql("SELECT * FROM employees WHERE department = 'IT'", engine)

# ... do analysis / feature engineering / modeling in pandas ...

# write results back to a new table
df.to_sql("it_department_summary", engine, if_exists="replace", index=False)
💼 Manager's Corner

Why we use this

DA/DS/MLE work rarely stops at SQL — pulling query results into pandas or writing them back with SQLAlchemy is the normal bridge between the database/warehouse and modeling or reporting code.

What the manager actually wants

They don't see this step directly, but this is how the numbers in their dashboard, or the features feeding a model, actually get there.

Alternatives

BI tools with native database connectors (Tableau/Power BI direct query) skip Python entirely for pure reporting; for ML specifically, a feature store (e.g. Feast) formalizes this SQL→features handoff so training and serving stay consistent.

📚 Bookstore Project Walkthrough

★ ImportantDADS

The course's capstone: a 3-table schema (Books, Customers, Orders) loaded from CSV, used to answer realistic business questions end to end.

CREATE TABLE Books(
    Book_ID SERIAL PRIMARY KEY,
    Title VARCHAR(100), Author VARCHAR(100), Genre VARCHAR(50),
    Published_Year INT, Price NUMERIC(10,2), Stock INT
);

CREATE TABLE Customers(
    Customer_ID SERIAL PRIMARY KEY,
    Name VARCHAR(100), Email VARCHAR(100), Phone NUMERIC(15),
    City VARCHAR(50), Country VARCHAR(150)
);

CREATE TABLE Orders(
    Order_ID SERIAL PRIMARY KEY,
    Customer_ID INT REFERENCES Customers(Customer_ID),
    Book_ID INT REFERENCES Books(Book_ID),
    Order_Date DATE, Quantity INT, Total_Amount NUMERIC(10,2)
);

Business questions → queries

-- most frequently ordered book
SELECT o.book_id, b.title, COUNT(o.order_id) AS freq_ordered
FROM Orders o JOIN Books b ON o.book_id = b.book_id
GROUP BY o.book_id, b.title
ORDER BY freq_ordered DESC;

-- the customer who spent the most, overall
SELECT c.customer_id, c.name, SUM(o.total_amount) AS spent
FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY spent DESC;

-- remaining stock after fulfilling all orders (LEFT JOIN + COALESCE handles
-- books that have never been ordered, where SUM(o.quantity) would be NULL)
SELECT b.book_id, b.title,
       b.stock,
       COALESCE(SUM(o.quantity), 0) AS total_ordered,
       b.stock - COALESCE(SUM(o.quantity), 0) AS remaining_stock
FROM Books b
LEFT JOIN Orders o ON b.book_id = o.book_id
GROUP BY b.book_id, b.title, b.stock
ORDER BY b.book_id;
💡 Why this project is a good portfolio piece
It touches nearly every skill in these notes in one place: schema design with foreign keys, CSV import, filtering, aggregation with GROUP BY/HAVING, joins (including LEFT JOIN for the "never ordered" case), and NULL-handling with COALESCE — exactly the mix an interviewer expects to see explained clearly.
